# ATLAS 2.0 — research and technology review

> **Historical v2 investigation.** Retained as supplied research history, not verified current product/model facts. The v4 work did not reaccess every cited original. See [the v4 upgrade](V4_UPGRADE.md) for implemented behavior and source-access limits.

Research date: 2026-11-03. Scope: point-in-time technical investigation, original-repository forensics, local implementation and empirical control tests. This is an engineering review, not a preregistered systematic review of every research-agent paper. The source register contains 77 dated primary documentation, original research and methodology records; the search log records scope, access failures and reconciliation of conflicting versions.

## Principal finding and evidence status

The original ATLAS has thoughtful research principles and a detailed intake/meta-research design. Its central weakness is the distance between those instructions and the software that checks them. Only two short Python scripts are executable; neither implements the lifecycle, authenticates an integration or establishes citation support. A status string can say COMPLETE without the work existing. The reconstruction therefore concentrates on executable controls around research, while keeping judgment with a researcher and an independent reviewer.

The selected architecture is a small local engine, a concise Claude Code entry point, six stage skills, five task-specific agents and project artifacts. No evidence establishes that this combination is universally optimal. It is an engineering choice that minimizes untested infrastructure while providing falsifiable behavior. Its superiority in real research accuracy remains an open empirical question.

| Evidence category | Meaning in this release | Examples |
|---|---|---|
| Demonstrated | Actual local execution with retained results | Sequential gates; blocked missing evidence; arithmetic; checkpoint recovery; synthetic lifecycle |
| Documented | Current official or original-source description | Claude skill/subagent layout; provider API offerings; framework persistence |

The full original ZIP is retained without modification, with hashes for every original file. Local control tests are separable from model behavior. The test report does not score factual accuracy, hallucination rates, independent reviewer agreement, latency or cost when these were not measured.

## A. Claude Code architecture and operational compatibility

Official instructions distinguish project memory, modular rules and on-demand procedural content. ATLAS keeps the lifecycle contract in a short root `CLAUDE.md`, a small safety/evidence rule and stage skills. The prototype's master installer duplicates 36 delivered payloads. Keeping that master in the active instruction path creates redundant authority and potential drift without adding execution. It is preserved only in the original reference archive. [CC01: Instruction hierarchy and memory](https://code.claude.com/docs/en/memory)

Skills are stored in `.claude/skills/<name>/SKILL.md`; their descriptions are discoverable while the body loads when used. Invocation controls matter: the release leaves ordinary stage skills model-invocable, while `/atlas-init` is explicitly user-invoked. A skill's `allowed-tools` field grants tool preapproval; it is not a restrictive allowlist. ATLAS omits it. The structural validator deliberately accepts only the simple YAML subset used by this release, not all legal YAML. [CC02: Skills and progressive disclosure](https://code.claude.com/docs/en/skills)

Subagents provide isolated context and an explicit `tools` list. Read-only reviewers omit shell/write/edit tools and persistent `memory`; that memory option can add writing capabilities. The quantitative agent has Bash and is consequently not read-only. All roles inherit the currently selected model, avoiding dependence on a model ID absent from the user's account. Actual model/version should be recorded when observable. No named model is silently inferred from a role label. [CC03: Custom subagents](https://code.claude.com/docs/en/sub-agents) [CC14: Model routing](https://code.claude.com/docs/en/model-config)

Teams are documented as experimental and have continuation/coordination restrictions. They are an optional future experiment, not the default scheduler. The current plan uses a coordinator and a task dependency graph, with separate branch artifacts. Tasks persist, but workers are not magically restarted after interruption. Durable local state and durable remote execution are different properties. [CC04: Experimental agent teams](https://code.claude.com/docs/en/agent-teams)

Settings, hooks, sandboxing and MCP are separate mechanisms. The release supplies an empty project settings object, no executable hooks, no MCP servers and no bypass permission mode. This keeps ordinary account/managed policy in force. A project instruction cannot itself create an OS or network sandbox. Authentication, tool visibility and environment restrictions must be observed in the real client. [CC05: Settings hierarchy](https://code.claude.com/docs/en/settings) [CC06: Hook lifecycle](https://code.claude.com/docs/en/hooks) [CC07: MCP configuration](https://code.claude.com/docs/en/mcp) [CC08: Security boundaries](https://code.claude.com/docs/en/security) [CC11: Sandboxed Bash](https://code.claude.com/docs/en/sandboxing)

Programmatic CLI execution, telemetry and plugin packaging are documented extension routes, but they are not needed for the local engine. A deployed automation service would need explicit session ownership, cancellation, timeout reconciliation and telemetry privacy controls. Plugins would mainly improve distribution, not establish evidence quality. ATLAS ships as an extractable project because that path has fewer moving parts here. [CC09: CLI execution](https://code.claude.com/docs/en/cli-reference) [CC10: Observability](https://code.claude.com/docs/en/monitoring-usage) [CC13: Plugin architecture](https://code.claude.com/docs/en/plugins)

Compaction and continuation are handled operationally by reading persisted mandate, protocol, state and task outputs. Do not rely on a compressed conversation to preserve source qualifiers. Context discipline and prompt caching may improve resource usage; their benefit depends on actual reuse and runtime billing. No token saving or cache hit rate was measured. Keep stable instructions compact and measure costs in deployment rather than increasing report length to occupy a large context window. [CC01: Instruction hierarchy and memory](https://code.claude.com/docs/en/memory) [CC12: Cost and context management](https://code.claude.com/docs/en/costs)

Compatibility conclusion: the layout is checked against the documentation accessed on the report date. Claude Code is not installed in this environment; command recognition, real intake conversation, tool isolation and stop behavior inside Claude remain runtime-unverified. The local initialization function was executed separately and is designed to emit the exact requested readiness sentence and exit without a project or network call.

## B. Models, research engines and independent evidence

A model's reasoning ability is only one component of a research system. Retrieval coverage, query strategy, source extraction, context handoffs, numerical tools and review can change the result. Comparing two branded research products confounds the underlying models with those surrounding systems. A model leaderboard should not be treated as a research-quality leaderboard.

The investigation did not locate a single independent, equal-resource, current evaluation that resolves the full requested matrix of reasoning, web retrieval, mathematical correctness, coverage, calibration, cost, latency and reliability for all these systems. Consequently no universal winner is named. BrowseComp is primarily difficult short-answer retrieval; it cannot establish the quality of a long decision report. The third-party OpenRouter results inspected also use different sample counts and configurations, making naive score ordering inappropriate. [EV01: BrowseComp](https://openai.com/index/browsecomp/) [EV10: OpenRouter BrowseComp runs](https://openrouter.ai/benchmarks/browsecomp/)

DeepResearch Bench adds report/citation evaluation. Its successor separates important report dimensions using expert-report-derived rubrics. These approaches are more relevant to ATLAS, but reference coverage, judge quality, contamination and task representativeness remain limitations. ATLAS's future evaluation should keep factual support, coverage, reasoning and presentation as separate outputs. Do not average fluency with correctness into an impressive but misleading single score. [EV02: DeepResearch Bench](https://arxiv.org/abs/2506.11763) [EV03: DeepResearch Bench II](https://arxiv.org/abs/2601.08536v3)

Recommended routing is a testable hypothesis: use the available capable coordinator for method selection and synthesis, the same or another capable independent context for material evidence review, and cheaper extraction only where a labeled pilot shows acceptable error. Use a second engine for distinct source discovery or adversarial hypotheses when the decision justifies the cost. Shared sources and correlated model training mean agreement is not independent replication. Escalate consequential disagreements to original data or a qualified human.

## C. Multi-agent architecture and frameworks

Research on scaling agent systems shows task-dependent gains and losses rather than a universal benefit from adding workers. The v3 paper accessed in this investigation differs from earlier search snippets; the latest version was used for the qualitative conclusion. Anthropic's engineering account offers useful orchestration lessons but remains a vendor-internal study with resource effects. Neither justifies a fixed number of agents for every inquiry. [AR01: Scaling Agent Systems](https://arxiv.org/abs/2512.08296v3) [AR02: Anthropic multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

The implemented organization is planner/coordinator → bounded independent branches → evidence/adversarial review → synthesis. The coordinator owns state and final artifacts. A worker receives the neutral mandate, one subquestion, allowed data scope, evidence requirements, stopping rule and output path. It does not begin with other workers' favored answer. Branches should partition independent work or isolate specialist context; they should not merely paraphrase the same search results.

Debate is used to surface falsifiable counterarguments and decision-reversing assumptions, not as a voting mechanism. The reviewer first tries to reconstruct support from sources, then compares the draft claim. Source-origin groups accompany merged evidence. A numerical majority of reports derived from one survey remains one underlying observation. The task DAG catches cycles and premature dependency starts, caps attempts and records missing outputs; it does not measure the value of a branch or automatically balance work.

This is not a claim that plain Python outperforms those frameworks. It is a bounded feasibility decision. Revisit it when requirements include concurrent long-running remote jobs, durable callbacks or multi-user scheduling, and benchmark the additional failure/recovery surface.

## D. Deep research methodology and completeness

Generalizable research controls are: explicit question/decision, operational definitions, alternatives, planned evidence, reproducible retrieval, source provenance, inclusion/exclusion reasons, measurement validity, uncertainty, counterevidence and decision-linked stopping. Domain-specific methods must remain domain-specific. A commercial market comparison should not claim GRADE certification; a clinical evidence review should not become an arbitrary weighted opportunity score.

For a systematic scientific review, use an appropriate question framework, protocol, reproducible database strategies, transparent screening and multiple-report/study linkage. PRISMA 2020 and PRISMA-S support reporting; they do not guarantee a well-conducted or unbiased review. Cochrane guidance informs search/selection. Risk of bias, inconsistency, indirectness, imprecision and publication bias affect certainty for specific outcomes. They are not interchangeable with a source's brand reputation. [ME01: PRISMA 2020](https://www.bmj.com/content/372/bmj.n71) [ME02: PRISMA-S](https://www.prisma-statement.org/prisma-search) [ME03: Cochrane search and study selection](https://www.cochrane.org/authors/handbooks-and-manuals/handbook/current/chapter-04) [ME04: GRADE criteria](https://www.cdc.gov/acip-grade-handbook/hcp/chapter-7-grade-criteria-determining-certainty-of-evidence/index.html)

For causal questions, distinguish association, prediction and intervention effects. Specify population, intervention/exposure, comparator, outcome and time, and identify confounding/selection/measurement assumptions. A regression coefficient alone is not a causal finding. For forecasting, use a time-respecting evaluation, relevant naive baselines and out-of-sample error, not training fit. The core does not implement a general causal estimator or statistical meta-analysis engine; specialist code must be separately specified and tested. [ME05: Causal Inference: What If](https://miguelhernan.org/whatifbook) [ME06: Forecasting: Principles and Practice](https://otexts.com/fpp3/toolbox.html)

For business, financial and technology decisions, use explicit alternatives, realistic counterfactuals, constraints and sensitivity. Public appraisal guidance is helpful for transparent option comparison, but its policy-specific discount rules must not be copied as generic private-company rates. Market size needs denominator definitions and overlap checks; attractive traffic or gross revenue is insufficient evidence of entrant profitability. [ME07: HM Treasury Green Book](https://www.gov.uk/government/publications/the-green-book--2)

The eight supplied profiles deliberately differ. Amazon research addresses marketplace/category feasibility, parent-child SKU estimates, seasonality, fees, returns and supplier validation. Shopify versus Amazon compares channel-specific acquisition, ownership of customer relationships, fulfillment, retention and cash timing. UAE versus US compares harmonized definitions and locally available data. Opportunity discovery adds base rates and validation experiments. Financial work reconciles filings and downside. Scientific work uses study-level screening. Technology work uses reproducible workloads and failure criteria. General investigations use claim trees, chronology, independent corroboration and alternative explanations.

Completeness is a coverage decision under constraints, not a count of sources. Every protocol dimension must be covered or have a recorded gap and decision impact. Stop when remaining accessible searches are unlikely to change the decision materially, results are stable under plausible assumptions, critical contradictions are resolved or expressly conditional, and further work exceeds justified resources. A hard access gap may warrant a partial conclusion rather than an invented estimate. The claim that marginal information value is low is itself a judgment to justify; it is not automatically estimated by the CLI.

## E. Meta-research and preparation

Mandatory meta-research begins only after intake ends. It studies how to investigate the question, not the final answer. The dossier compares at least two approaches, records current method sources, needed expertise, tools, risks, limitations and a pilot. The protocol then specifies coverage, searches, inclusion/exclusion, verification, stopping and amendment rules. The CLI requires these artifacts before readiness; it cannot certify their intellectual quality.

The core bounds a preparation cycle to one to three passes. This limit is an engineering default against recursive preparation, not a scientific optimum. Start with a minimal appropriate design; use the pilot to expose missing data, inconsistent definitions, extraction errors or access barriers. A larger redesign requires a recorded amendment/reopen reason. Stop preparing when the data and analysis are feasible enough to investigate meaningfully, or when the limitation is understood well enough to explain what cannot be concluded.

Readiness is not binary tool optimism. It checks methodology, evidence, computation, tools, budget, permissions and verification. A “limited” result needs a specific fallback. A failed required tool cannot be renamed “tested.” Methodological memory can offer candidate recipes; current domain standards and the present question must still determine the choice. Pilot evidence should reveal whether a tool adds information over the simpler baseline, not merely whether its endpoint returns HTTP 200.

## F. Reliability, provenance and claim support

Atomic-claim evaluation is more diagnostic than a single report label; citation correctness and coverage are different from fluent writing. Later research specifically examines failures in deep-research attribution, live tasks, evaluator labels and inter-agent handoffs. These findings motivated explicit claim/source/reviewer records, but this release does not implement those papers' evaluators or inherit their measured performance. [EV04: FActScore](https://aclanthology.org/2023.emnlp-main.741/) [EV05: ALCE](https://aclanthology.org/2023.emnlp-main.398/) [EV06: DeepTRACE](https://proceedings.iclr.cc/paper_files/paper/2026/hash/ad08767706825033b99122332293033d-Abstract-Conference.html) [EV07: LiveResearchBench](https://proceedings.iclr.cc/paper_files/paper/2026/hash/998f8d8ff2697da2eae5f87143668754-Abstract-Conference.html) [EV08: DeepFact](https://aclanthology.org/2026.acl-long.1586/) [EV09: Who is the Agent to Blame?](https://aclanthology.org/2026.emnlp-main.1681/)

The executable verifier checks IDs and references, eligible URL shape, local snapshot hashes, dates/freshness, exact excerpt occurrence, review fields, distinct author/reviewer labels, unresolved contradictions, repeated byte content, calculation reproduction and numeric output bindings. A derived number must match a reproduced output pointer and its unit map. A reported statistic is separately labeled and still requires source review.

These controls deliberately do not say “the claim is true.” An excerpt can be real but misapplied; a URL can resolve to an unreliable page; two reviewer labels can belong to one process; different article bytes can recycle one original statistic. The review instructions require opening the source, checking qualifier/denominator/date/geography, tracing the original study and recording why it supports the precise claim. A source-origin field is an auditable assertion, not an automatically discovered dependency graph.

Material claims require independent supporting assessments and a review gate. Contradictions need explicit resolution or conditional narrowing. No automatic semantic NLI judge is installed: that would add another fallible model, access cost and calibration problem. A future entailment model may triage cases after a labeled error study, while consequential claims remain subject to source-grounded review. High-stakes professional judgments may require qualified human verification identified in the protocol.

## H. Quantitative and decision science

Implemented calculators use explicit inputs and assumptions; none predicts a market by generating plausible numbers. Decimal arithmetic handles unit economics, cashflow, Bayesian updates, MCDA and EVPI. A seeded discrete joint-scenario sampler produces conditional distribution summaries. Each result records input hash, engine version and output units; evidence verification recomputes it and binds derived claims to outputs.

Unit economics separates gross price, VAT, net-based fee assumption, landed/fulfillment/acquisition/return costs, fixed costs and volume. Cashflow distinguishes timing from booked revenue and opening cash from initial investment. Contract-specific fee bases or accounting rules must be amended explicitly. The tool is not a tax engine. Assumptions need traceable inputs or visibly declared scenarios, and all material calculations need independent review.

Scenario probabilities are supplied, not inferred. Joint scenarios preserve assumed dependencies; they are not a fully general correlated stochastic simulator. Simulation percentiles are not confidence intervals. MCDA uses fixed bounds, stated benefit/cost direction and local weight sensitivity; additive utility and non-overlapping criteria require substantive justification. EVPI is an upper bound under specified payoffs/probabilities, not the value of a particular research subscription. Bayesian results are conditional on the stated prior and likelihoods; no calibrated forecasting skill is implied.

Further rigor depends on the task: source-data validation, domain statistics, missingness, sample design, causal identification, out-of-sample tests and robust stress scenarios. The release supports audited project-specific code but does not pretend to contain every scientific estimator. A small trustworthy arithmetic layer is preferable to a broad collection of unvalidated financial and statistical formulas.

## I. Memory and controlled improvement

Project evidence, project state and reusable methods are separate. Active method memory accepts only a validated method proposal with scope, reviewer, receipt, hash and expiry. Promotion is explicit; earlier versions are archived. Expired methods are excluded from ordinary retrieval. Topic conclusions and user preferences are not generalized into cross-project facts. Receipt existence does not establish that an experiment was valid, so methodological review remains essential.

Semantic memory retrieval is deferred. Exact lexical retrieval is implemented and transparent, sufficient for a small library. Embeddings become worth considering only after a retrieval evaluation shows relevant methods are being missed at useful scale. An embedding score would rank candidates, not validate them. No automatic core self-modification or silent promotion is enabled.

Tool observations are dated and expire. A successful historical test is not perpetual access. New method versions should use the same held-out cases and controls as their predecessors, retain failures and be reversible. Improvements in a local validation metric must not be described as improvements in practical decision quality without independent outcome evidence.

## J. Security, reliability and autonomous limits

The threat model includes malicious source instructions, prompt-injection through tool responses, dependency compromise, secrets in configuration, source laundering, billing uncertainty and corrupt/partial state. The executable core makes no network requests, installs no dependencies, evaluates no retrieved code and uses no pickle. Controlled paths reject traversal and symlinks; JSON input is bounded and rejects duplicate keys/nonfinite constants. These are local controls, not comprehensive red-team proof. [SE01: NIST Generative AI Profile](https://doi.org/10.6028/NIST.AI.600-1)

SQLite transactions replace free-form state JSON. Event receipts link state and task/cost ledgers; stage gates hash accepted artifacts. Checkpoints use SQLite's backup API and receipts. Explicit reopen invalidates downstream acceptance, while verified restore preserves the prior database for inspection. Backup covers the database; source/output files need a separate full-project backup. These choices follow the database's documented transaction/backup facilities and were exercised in local tests. [SE03: SQLite atomic commit](https://www.sqlite.org/atomiccommit.html) [SE04: SQLite online backup](https://www.sqlite.org/backup.html)

The CLI is not a security reference monitor for Claude. A filesystem owner can rewrite both data and hashes; a model can take actions outside the CLI; a tool allowlist is not a guarantee against indirect prompt injection. Real deployment needs appropriate OS permissions, sandboxing, provider scopes, privacy review and independent model-facing adversarial testing. Logs must not contain secrets. The zero-budget ledger prevents recording unauthorized local costs but cannot enforce remote provider billing or recover an ambiguous external job without an actual adapter.

The single-coordinator design reduces competing writes, but it is not a distributed service. Retries are bounded in the task ledger and require explicit transitions. Missing outputs, invalid artifacts and failed checks block progress. Recovery should prefer verifiable artifacts over inferred conversational completion. Failure should result in a specific limitation or corrected artifact, never a silently downgraded standard.

## Architecture decision and remaining evidence

The implementation removes the largest avoidable mismatch: instructions without enforcement. It retains the prototype's best principles—interview first, mandatory method research, source independence, skepticism about commercial estimates and conditional conclusions—while adding checks whose behavior can be reproduced. It consolidates redundant specialist roles and separates configuration from tested capability.

Formal release acceptance is limited to completed local tests, complete original-file accounting, documented compatibility, reproducible packaging and explicit unresolved criteria. Real Claude execution, live provider smoke tests, expert post-implementation review and blinded original-versus-upgraded research trials are still required before claiming measured research superiority. The supplied evaluation protocol specifies how to conduct those trials without inventing scores.
